# Crypto {Kurt} Ai — PUMP/DUMP Scanner v1.0

Отдельный проект, не связанный с ботом RSI/OI. Серверные функции Vercel, Bybit v5 public API, Upstash Redis REST, Telegram Bot API. Секреты никогда не добавлять в GitHub.

## Установка
1. Создать **новый** GitHub репозиторий и загрузить содержимое этой папки в корень.
2. Создать **новый** проект Vercel из репозитория (Framework Preset: Other). Установить Node 20+.
3. Создать отдельную Redis database в Upstash.
4. Добавить переменные в Vercel (Settings → Environment Variables):
   - `CRON_SECRET` — случайная длинная строка.
   - `TELEGRAM_BOT_TOKEN` — токен отдельного Telegram бота.
   - `TELEGRAM_CHAT_ID` — ID чата.
   - `UPSTASH_REDIS_REST_URL` — REST URL базы.
   - `UPSTASH_REDIS_REST_TOKEN` — REST token базы.
   - `BATCHES=6`
   - `MAX_COINS=180`
   - `MIN_TURNOVER_USDT=3000000`
   - `MIN_REL_VOLUME=2.5`
5. Redeploy в Vercel.
6. В cron-job.org создать 6 заданий GET `https://YOUR-APP.vercel.app/api/scan?batch=0` ... `batch=5`. Каждое раз в **2 минуты**, со смещением запуска на 15–20 секунд относительно предыдущего задания, чтобы не перегружать API. В каждом задании указать HTTP header `Authorization: Bearer ВАШ_CRON_SECRET`.
7. Добавить седьмое задание `https://YOUR-APP.vercel.app/api/report` каждые 30 минут, с тем же заголовком.
8. Проверить в истории cron-job.org HTTP 200 и JSON `{ "checked": ..., "errors": ... }`.

## Логика
1-минутные **закрытые** свечи, изменение цены 1/5/15 мин, относительный объём относительно предыдущих 60 мин, аномальность изменения цены, пробой 20-минутного диапазона. EARLY: 5 мин >=2%, объём x2.5, аномальность x2, ускорение. CONFIRMED: >=4%, объём x3.5, аномальность x2.5, пробой диапазона. EXHAUSTION: только после EARLY/CONFIRMED того же направления, обратное минутное движение и повышенный объём. OI выводится справочно, не служит обязательным фильтром.

## Важные ограничения
- Раннее обнаружение не гарантирует продолжения движения; пороги требуют проверки на истории.
- Если сканирование одной партии занимает >60 сек, уменьшить MAX_COINS или увеличить BATCHES.
- Данные OI сравниваются с прошлым сканированием, а не с биржевыми историческими свечами OI.
- Отчёт считает число уведомлений, **не** число уникальных монет и не доходность.
- Бесплатные лимиты Vercel/cron-job.org могут не поддерживать указанную частоту.

## v1.1 — WHALE DETECTOR
- Включён по умолчанию: `WHALE_ENABLED=true` (для отключения `false`).
- `WHALE_MIN_TRADE_USD=100000` — минимальный размер **одного исполнения** в USDT для уведомления. Установи, например, `250000` для меньшего количества сообщений.
- Использует Bybit `/v5/market/recent-trade` (последние 1000 сделок по каждой монете) и сравнивает идентификаторы/время с предыдущим опросом. Первый опрос только запоминает состояние.
- Уведомления показывают крупные агрессивные Buy/Sell и суммы Buy/Sell в доступной выборке. Это НЕ установление личности кита, НЕ перевод токенов и НЕ доказательство открытия LONG/SHORT.
- **Ограничение:** при опросе партии раз в 6 минут активные монеты могут совершить >1000 сделок между запросами. В таком случае часть сделок будет потеряна. Для полного потока требуется постоянный WebSocket-сборщик (не обычные короткие функции Vercel). Суммы выборки нельзя считать полным оборотом за 5 минут.
- Дополнительные запросы увеличивают время сканирования и нагрузку на API. При таймаутах уменьшай `MAX_COINS` или повышай число партий; проверяй Vercel Logs.

## v1.2 — динамический выбор рынка (HOT + DISCOVERY)
- Вместо фиксированного топ-180 по обороту: `HOT_COINS=30` и `MAX_COINS=180` (150 мест для DISCOVERY).
- HOT: в первую очередь монеты, где за последние 30 минут уже обнаружен EARLY/CONFIRMED; оставшиеся места заполняются по абсолютному изменению цены за 24ч среди ликвидных монет. Последний показатель — грубый предварительный фильтр, **не** показатель минутной аномалии и не прогноз.
- DISCOVERY: остальные ликвидные монеты в алфавитном порядке, с вращающимся окном. Каждые 6 минут окно смещается на 150 монет (при `BATCHES=6` и расписании одна партия в минуту). Таким образом покрываются монеты за пределами HOT.
- Каждый вызов `/api/scan?batch=N` берёт приблизительно 1/6 HOT и DISCOVERY; при изменении HOT между запусками возможны повторы/пропуски на границах циклов.
- Сканирование НЕ гарантирует обнаружение каждой крупной сделки: опрос recent-trade ограничен последними 1000 исполнениями по символу. Для непрерывного полного покрытия необходим отдельный WebSocket-коллектор.
- `MIN_TURNOVER_USDT=3000000` остаётся фильтром ликвидности. Монеты ниже порога исключены из наблюдения.
- Cron-расписание и URL не меняются. Добавь `HOT_COINS=30` и сделай Redeploy. Можно сохранить существующий Redis и переменные.
